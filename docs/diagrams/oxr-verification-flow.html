Why OXR needs a graphics card

It actually looks at the page. The app today just copies text that's already inside a PDF. OXR looks at the picture of the page, the way a person would: it finds the tables and paragraphs, then reads them.

That takes a lot of math, fast. Graphics cards are built for exactly this kind of math. OXR's makers say you need a high-end NVIDIA card with at least 24 GB of memory (48 GB or more is better).

It reads many pieces at once. Once OXR is loaded onto the card, it can read lots of tables at the same time instead of one by one. A small program called oxr serve lets our app send it pages, the same way we used the free online version.

No way to run it without a graphics card is documented. For this test we used OXR's free online version: 4.90–11.39 seconds per page, including waiting in line. We haven't timed our own rented card yet.

Why OXR needs a GPU

It's a neural network, not a text extractor. pypdf just copies text that's already in the PDF. OXR looks at the picture of the page: first a layout model (D-FINE) draws boxes around tables, text and figures, then a 1.3-billion-parameter vision-language model reads each box.

Weights live in GPU memory (VRAM). 1.3B parameters × 2 bytes each in BF16 is about 2.6 GB of weights. On top of that sits the working memory for the image tokens being read. SoMark's README asks for an NVIDIA GPU with BF16 support, CUDA 13.0, at least 24 GB to start, and 48 GB or more recommended.

vLLM keeps the GPU busy. vLLM is the serving engine. It loads the model once and pushes many page regions through together (batching) instead of one at a time. oxr serve wraps all of this in an HTTP API we can call the same way we called the free one.

No CPU-only path is documented. The test used SoMark's free hosted API instead: 4.90–11.39 s per page, including network time and queueing. Self-hosted GPU speed has not been measured yet.

Keeping owners' manuals private

Everything we've sent so far was free, public material (an FAA handbook and a 1940s Army manual). Owners' manuals are usually copyrighted. For those: read them on our own rented machine (the more private option), don't send pages to outside services, and wipe the machine when done. Check 3 currently sends table pictures to an outside service. For copyrighted pages we'd either run that AI on our own rented card too, or first check how that service handles data. Manual PDFs never go into the code repo.

Owners' manuals are usually copyrighted, so for real uploads: run OXR on a Secure Cloud pod, keep pages off third-party APIs, and delete the pod's volume when finished. Layer 3 currently sends table crops to OpenRouter. For copyrighted pages, either run a vision model (e.g. Qwen3-VL) on the same pod or confirm the provider's data terms first. Manual PDFs are never committed to the repo (AGENTS.md).

Asking it fresh beats asking "is this right?"

Fresh: the second AI reads the table without seeing OXR's answer, then we compare. "Is this right?": we show it OXR's answer and ask. That version mostly said yes. On its own it waved through 47 of 261 wrong-row numbers, and it wrongly doubted 350 of 6,212 correct numbers (5.6%). The fresh way was also cheaper, because one read per table covers every number. And it was consistent: across repeat runs it misread 1 number in 1,008 ("4 3/8" read as "4⅝").

Blind beats confirm

Blind: the model transcribes the crop without seeing OXR's answer, then we compare. Confirm: we show OXR's answer and ask "is this right?". Confirm tended to agree. Used alone it accepted 47 of 261 row shifts, and it called 350 of 6,212 correct control cells (5.6%) mismatches. Blind was also cheaper: one transcription per table serves every check. Blind was stable across repeats too: 1 misread in 1,008 cell readings ("4 3/8" read as "4⅝").

Fine print

  • Small test: 9 pages from 2 manuals. Real owners' manuals (different layouts, photos, worse scans) haven't been tried.
  • The wrong-row and changed-digit mistakes were faked by us, not made by OXR. They show what each check can catch.
  • We haven't timed or priced our own rented graphics card. Every OXR run used the free online version.
  • Without OXR's second try as one of the readers in check 2, that check wrongly doubted 31 correct numbers. The second try is what keeps it from crying wolf.
  • Check 4 (show the photo), saving how sure we are in the library, and the answer format are ideas, not built yet. Today the app saves each page as one blob of text.

Where the numbers come from: the spike's result files (oxr-test/summary.md, verify/summary.md, verify3/summary.md) and the comments on issue #163. The table photos are from TM 9-1730A (public domain, archive.org).

Caveats

  • Small sample: 9 pages from 2 manuals. Real owner manuals (other layouts, photos, worse scans) are untested.
  • Row shifts and digit swaps were injected by us, not produced by OXR. They show what each layer can catch.
  • Self-hosted GPU throughput and cost per page are not measured. All OXR runs used the free hosted API.
  • Without the OXR 300-dpi re-run as a third reader ("strict mode"), the vote produced 31 false flags. The re-run is what keeps L2 from flagging correct values.
  • Layer 4 (show crop), per-value states in the RAG index, and the cited answer are proposed designs, not built. Today backend/ingest.py uses pypdf with one chunk per page.
